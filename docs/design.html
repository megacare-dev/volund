คะแนนของงานแบบ constraint + objective

s = 0.4·p + 0.6·G·O′
  • p คือสัดส่วนของ constraint ที่ผ่าน
  • G เป็น 0 ทันทีถ้าพลาด hard constraint แม้ข้อเดียว คะแนนจึงตันที่ 0.4
  • O′ คือผลด้าน objective (เช่น ต้นทุน น้ำหนัก) เทียบกับคำตอบที่ไม่ได้ optimize

ลำดับที่ถูกจึงเป็น ผ่าน hard constraint ให้ครบก่อน แล้วค่อย optimize

อันดับคิดแบบ Pareto

อันดับสุดท้ายดูจากคะแนน Stage 2 แต่ entry ต้องอยู่บนเส้น Pareto ระหว่างคะแนนกับต้นทุน และคะแนนเฉลี่ยต้องไม่ต่ำกว่า 0.138

แปลว่าทีมที่คะแนนสูงสุดอยู่บนเส้นเสมอ ส่วนทีมอื่นต้อง ถูกกว่าทุกทีมที่คะแนนสูงกว่าตัวเอง ต้นทุนจึงเป็นตัวแปรที่เราต้องคุมได้ตั้งแต่ต้น (effort, จำนวนรอบแก้, งบต่อ phase)

ภาพรวมระบบ

Völund เป็น WebSocket server ใน serve container มันไม่ได้แตะไฟล์โจทย์โดยตรง ทุกอย่างทำผ่านคำขอที่ evaluator ไปรันให้ใน task container

กติกาของ protocol ที่ต้องระวัง

  • frame ละไม่เกิน 16 MiB และรันพร้อมกันได้ไม่เกิน 8 request
  • ส่ง frame ผิดรูปแบบเกิน 20 ครั้ง task จบทันที
  • ได้ cancel แล้วมีเวลา 10 วินาทีให้ส่ง done

คำสั่งใน task container

  • exec คือ bash -c ใน shell ใหม่ทุกครั้ง cd กับ export ไม่ติดไปคำสั่งถัดไป
  • รันได้นานสุด 600 วินาทีต่อคำสั่ง output เกิน 100 KB เหลือแค่หัวกับท้าย
  • อ่านเขียนไฟล์ได้ครั้งละไม่เกิน 10 MB

เรื่องของโมเดล

  • เรียกโมเดลอื่นนอกจากที่ประกาศไว้จะได้ 403
  • Opus 5.5 ไม่รับ temperature, top_p และการบังคับ tool
  • ต้องเก็บข้อความของโมเดลเป็น JSON ดิบ ไม่อย่างนั้นข้อมูลอย่าง thought signature จะหายแล้วรอบถัดไปพัง

หนึ่ง task เดินอย่างไร

เส้นทางเป้าหมายของ M2–M3 ตอนนี้ (M1) ยังเป็น loop เดียว แต่ส่วนต้นกับส่วนท้ายทำงานแบบนี้แล้ว

  1. รับงาน evaluator เปิด WebSocket แล้วส่ง task มา มีโจทย์, โฟลเดอร์ทำงาน, เวลาที่เหลือ และรายชื่อ MCP server (ถ้ามี)
  2. PROBE โค้ด สำรวจไฟล์และเครื่องมือใน container (python, library, ตัวแปลง pdf) และขอรายชื่อ tool ของแอป โดยไม่เรียกโมเดลเลย
  3. INTAKE LLM โมเดลอ่านโจทย์กับไฟล์ แล้วบันทึกลง World ว่าต้องส่งอะไร ที่ไหน ใช้ค่าอะไรจากไหน และมี constraint อะไรบ้าง
  4. MODEL → SOLVE LLM เขียนโมเดลคำนวณพร้อมเทสต์ไว้ใน /tmp/volund/model/ harness เป็นคนรันเทสต์เอง จากนั้นหาคำตอบที่ผ่าน hard constraint ก่อน แล้วค่อย optimize
  5. WRITE LLM เขียนโครงไฟล์งานส่งตั้งแต่ต้นแล้วค่อยเติมให้ครบ ทำ action ในแอปจริง (ส่งอีเมล ปิดเคส) แล้วอ่านกลับเพื่อยืนยัน
  6. CHECK โค้ด ตรวจแบบไม่ใช้โมเดล: ไฟล์อยู่ครบและไม่ว่าง, เปิดได้ตาม format, ไม่มีไฟล์ทดค้างในโฟลเดอร์ที่ถูกตรวจ
  7. VERIFY ↺ FIX LLM ใช้ context ใหม่คำนวณซ้ำด้วยวิธีอื่นเพื่อหาช่องโหว่ ถ้าเจอก็แก้ แต่จะเก็บผลการแก้ไว้เฉพาะเมื่อคะแนนประมาณไม่ลดลง
  8. FINALIZE โค้ด สร้าง final_message จาก World (ไฟล์และ path, ผลหลัก, code ที่ใช้, สมมติฐาน, ข้อจำกัด) แล้วส่ง done

ทุกขั้น: ถ้าได้ cancel หรือเวลาใกล้หมด ให้กระโดดไป FINALIZE ทันที ซึ่งสรุปจาก World ได้โดยไม่ต้องรอโมเดล เราจึงมี done ที่มีเนื้อหาเสมอ

World Model

บทสนทนากับโมเดลไม่ใช่บันทึกหลัก สิ่งที่ขั้นหลังต้องใช้ทั้งหมดต้องอยู่ใน World

ชั้นที่ 1: สถานะของโปรเจกต์

ส่วนเก็บอะไร
deliverablespath, format, สถานะ Missing → Draft → Written → Checked
paramsค่า, หน่วย และที่มา (ไฟล์, หน้า, clause หรือ cell)
constraintshard หรือ soft, ค่าที่คำนวณได้, ผ่านหรือไม่
actionsaction ในแอป Pending → Done → Verified (ยืนยันด้วยการอ่านกลับ)
model, checks, issuesผลเทสต์ที่ harness รันเอง, ผล CHECK, ช่องโหว่ที่ VERIFY พบ

ชั้นที่ 2: โมเดลคำนวณที่รันได้

อยู่ใน task container ที่ /tmp/volund/model/

  • model.py สูตรของโปรเจกต์ เช่น load → shear หรือขนาดสาย → voltage drop และราคา
  • tests.py เทียบกับค่าที่เอกสารให้มา บรรทัดสุดท้ายพิมพ์ {"total": N, "passed": M} และ harness รันเอง ไม่เชื่อคำบอกของโมเดล
  • solve.py ไล่หาทางเลือก ผ่าน hard constraint ก่อนแล้วค่อยลด objective

3 ฟังก์ชันที่ใช้ตัดสินใจ

  • brief() เขียน World เป็นข้อความใส่ทุก prompt พอ context เต็มก็ตัดของเก่าทิ้งแล้ว render ใหม่ ไม่ต้องสรุปบทสนทนา
  • finish_blockers() ด่านก่อนจบ บอกว่ายังขาดอะไร
  • quality() ประมาณคะแนนในรูปเดียวกับ grader ใช้ตัดสินว่าจะเก็บผลการแก้หรือ rollback

ใครเขียนอะไร

  • harness: ส่วนที่หาได้แน่นอน เช่น รายชื่อไฟล์, ผลเทสต์, ผล CHECK
  • โมเดล: เขียนผ่าน tool world_deliverable, world_param, world_constraint, world_action และอื่น ๆ

เมื่อข้อมูลขัดกัน

ไฟล์งานส่งชนะเสมอ เพราะเป็นสิ่งที่ถูกตรวจ ให้อ่านไฟล์แล้วปรับ World ตาม ห้ามทำกลับทาง

Phase State Machine

โค้ดเป็นคนตัดสินว่าจะไปขั้นไหนต่อ ไม่ใช่โมเดล เพราะโมเดลมักหยุดก่อนงานเสร็จหรือวนอยู่ที่เดิม

ใช้ LLM โค้ดล้วน ไม่เรียกโมเดล ฟังก์ชัน next() เป็น pure function จึงเทสต์ได้โดยไม่ต้องมีโมเดล

งบเวลาตั้งต้นของแต่ละ phase

INTAKE 10%
MODEL 20%
SOLVE 15%
WRITE 20%
VERIFY 10%
FIX 15%
อื่น ๆ
PROBE ≤ 2 นาที, CHECK สั้น ๆ FINALIZE กันไว้ 4 นาทีเสมอ ตัวเลขเป็นค่าตั้งต้น จะปรับตามผลวัดใน M5

กติกาที่ใช้ทุก phase

  1. cancel หรือเวลาเหลือน้อย → FINALIZE
  2. งบของ phase หมด → เดินหน้าเสมอ ห้ามค้าง เช่น MODEL ที่เทสต์ยังไม่ผ่านก็ไป WRITE ด้วยสิ่งที่มี
  3. ก่อน FIX ให้ snapshot ไฟล์งานส่งและ World ถ้าแก้แล้ว quality() ลดลงให้ rollback แล้วจบ ไม่เสี่ยงทำของดีให้พัง
  4. ข้าม phase ได้ตามสิ่งที่อยู่ใน World ห้ามแยกทางตาม task id, ชื่อ หรือ path ของงาน dev

ทำไมไม่ปล่อยให้โมเดลคุมเอง

  • งานยาวถึง 6 ชั่วโมง context ยาวขึ้นเรื่อย ๆ โมเดลลืมข้อกำหนดตอนต้น
  • โมเดลชอบประกาศว่าเสร็จก่อนงานครบ ด่านก่อนจบกันเรื่องนี้
  • การตรวจงานตัวเองใน context เดียวกันมักเห็นด้วยกับตัวเอง VERIFY จึงใช้ context ใหม่
  • ต้นทุนคุมได้ เพราะทุก phase มีงบ

หลักการ 14 ข้อ

ใช้ตรวจทุกการเปลี่ยนแปลงของ harness

วิศวกรรม

  1. ผ่าน hard constraint ให้ครบก่อน แล้วค่อย optimize
  2. ตัวเลขทุกตัวได้จากโค้ดและมีหน่วยกำกับ เก็บ script ไว้เป็นหลักฐาน
  3. อ่านแบบด้วยการดูภาพ (render แล้วซูม) ไม่พึ่งแค่ข้อความที่ดึงออกมา
  4. งาน world ต้องทำ action จริงในแอปและยืนยันด้วยการอ่านกลับ

ความถูกต้อง

  1. World เป็นแหล่งความจริงของสิ่งที่ต้องทำ ไฟล์เป็นแหล่งความจริงของผลลัพธ์
  2. ตรวจ 2 ชั้น: โค้ด (CHECK) แล้วตามด้วย context ใหม่ (VERIFY)
  3. ด่านก่อนจบกันการหยุดก่อนเวลา

การส่งงาน

  1. ต้องมีงานส่งอยู่เสมอ: เขียนโครงตั้งแต่ต้น และ done ต้องไม่ว่างแม้โดน cancel
  2. final_message เป็นส่วนหนึ่งของงาน: ไฟล์และ path, ผลหลัก, code และมาตรฐาน, สมมติฐาน, ข้อจำกัด

ต้นทุน

  1. ปรับต้นทุนจาก effort, จำนวนรอบ, งบต่อ phase และ best-of-N
  2. ประหยัด context: PROBE ไม่ใช้ LLM, ตัด output เก็บหัวท้าย, render ใหม่จาก World, ใส่ cache mark
  3. คิดอันดับแบบ Pareto: ต้องถูกกว่าทุกทีมที่คะแนนสูงกว่า

การแข่งและการทดลอง

  1. ใช้ได้ทั่วไป ห้ามผูกกับงานใดงานหนึ่ง แยกวิธีตามประเภทงานส่ง ไม่ใช่ตาม task
  2. วัดทุกครั้งและเปลี่ยนทีละอย่าง จดสิ่งที่ไม่ได้ผลไว้ด้วย

  • ขนาดอย่างน้อย 16 vCPU, 64 GB, ดิสก์ 300 GB ได้ 2 ช่อง
  • ค่าโมเดลทั้งของ harness และของ judge คิดจากโปรเจกต์ GCP ของเรา ต้องตั้งงบก่อน

Ablation: เพิ่มทีละชั้นแล้ววัด

  1. A0sample custom-openai ของผู้จัด (baseline)
  2. A1Völund แบบ loop เดียว ต้องได้เท่า A0 พร้อม
  3. A2+ PROBE
  4. A3+ World และการ render ใหม่จาก World
  5. A4+ State Machine และด่านก่อนจบ
  6. A5+ MODEL/SOLVE (โมเดลคำนวณที่รันได้)
  7. A6+ VERIFY และการเก็บผลเมื่อคะแนนไม่ลด
  8. A7+ view_page (ดูแบบเป็นภาพ)

และ scaling: effort low/medium/high × จำนวนรอบแก้ 0–3 × best-of-N บนโมเดลที่จะส่งและอีกอย่างน้อย 1 ตระกูล

Milestones

ช่วงเวลาเป็นแผน วันส่งจริงคือ 4 ม.ค.

  1. M0
    15–17 พ.ย. เสร็จส่วนใหญ่
    โครง repo, สิทธิ์ dataset, ตั้งโปรเจกต์ GCP รอ, ทีมอ่านโจทย์ dev 3–4 งาน
  2. M1
    18–24 พ.ย. เสร็จยกเว้นส่วนที่ต้องใช้โมเดลจริง
    server, LLM client, loop เดียว, submission.yaml, kit check ผ่านบน Mac, baseline A0 รอ GCP
  3. M2
    25 พ.ย.–1 ธ.ค. เริ่มแล้ว
    driver + World + State Machine + tool + MCP, รันเต็มชุดครั้งแรกบน VM, ติดป้ายสาเหตุที่พลาด
  4. M3
    2–8 ธ.ค. แผน
    MODEL/SOLVE, CHECK, VERIFY, ด่านก่อนจบ, เทียบ 2 โมเดลขึ้นไปแล้วเลือกโมเดล
  5. M4
    9–15 ธ.ค. แผน
    view_page, ตัวตรวจการแพ็ก, ขั้น optimize, ablation
  6. M5
    16–22 ธ.ค. แผน
    กราฟคะแนนกับต้นทุน, ทดสอบ cancel และ retry, ปรับงบต่อ phase
  7. M6
    23–29 ธ.ค. แผน
    หยุดเพิ่มฟีเจอร์, รันเต็มชุด 2 รอบด้วยโมเดลที่จะส่ง, artifacts/
  8. M7
    30 ธ.ค.–4 ม.ค. แผน
    writeup ไม่เกิน 2,000 คำ + 3 รูป + ภาพปก, kit check ได้ ready to submit, ส่ง

บทบาททีม

ให้ทีมตกลงกันว่าใครรับสายไหน

Core (Rust)

server, LLM client, driver, MCP

Tools และเอกสาร

PROBE, CHECK, view_page, ตัวตรวจการแพ็ก

วิธีทางวิศวกรรม

playbook ตามประเภทงานส่ง, checklist ของ VERIFY, ไล่ดูงานที่พลาดด้วยสายตาวิศวกร ต้องมีพื้น EE หรือ ME เพราะงาน test ลับเป็น ME กับ EE รวมกัน 73%

Eval และ writeup

รัน eval, ติดป้ายสาเหตุ, ablation, ทำรูป, เขียน writeup

สิ่งที่ยังไม่รู้

  1. ใน task container มี python และ library อะไรบ้าง มีตัวแปลง pdf หรือ libreoffice ไหม และ /tmp เขียนได้หรือไม่
  2. gateway รับรูปภาพสำหรับโมเดลที่จะใช้หรือไม่ (มีผลกับหลักข้อ 3)
  3. ค่าใช้จ่ายต่อ 1 งานของแต่ละโมเดล
  4. โครงสร้าง submission.zip ที่แต่ละงานต้องการ (อ่านจากโจทย์เท่านั้น)

Fair play

  • ห้ามอ่านหรือใช้ grader และไฟล์อ้างอิงของงาน dev
  • artifacts/ ต้องมาจาก eval/run.py ด้วย harness และโมเดลที่ส่งจริง ห้ามแก้ด้วยมือ
  • ห้ามติดต่อ host อื่นนอกจาก model endpoint และห้ามเก็บหรือเผยแพร่ไฟล์ของงาน test
  • ห้าม hard-code คำตอบหรือแยกทางตาม task

คำศัพท์

สำหรับคนในทีมที่ไม่ได้อยู่สายซอฟต์แวร์

Harness
โปรแกรมที่พาโมเดลทำงาน: ส่ง prompt, รับคำสั่งที่โมเดลอยากรัน, ไปรันให้, ส่งผลกลับ และตัดสินว่าเมื่อไรพอ สิ่งที่เราส่งแข่งคือตัวนี้
Serve container
เครื่องจำลองที่ harness ของเรารันอยู่ ออก network ได้แค่ไปหาโมเดล
Task container
เครื่องจำลองที่มีไฟล์โจทย์ ทุกคำสั่งรันที่นี่ และ grader ตรวจไฟล์ที่นี่
Deliverable
ไฟล์งานส่งที่โจทย์สั่ง เช่น รายงาน, spreadsheet, zip, ไฟล์ IFC
Hard constraint
ข้อกำหนดที่พลาดไม่ได้ พลาดข้อเดียวคะแนนตันที่ 0.4
Rubric / judge
เกณฑ์ให้คะแนนที่ LLM (Claude Opus 5.5) ใช้อ่านงานแล้วให้คะแนน
MCP
มาตรฐานที่แอปใช้เปิด “tool” ให้ AI เรียก ในงาน world แอปอย่างอีเมลหรือระบบเอกสารเปิด tool ผ่าน MCP
World Model
บันทึกกลางของ harness ว่าตอนนี้รู้อะไรและต้องทำอะไร ไม่ได้พึ่งความจำของโมเดล
State Machine
กฎในโค้ดที่บอกว่าจากขั้นนี้ไปขั้นไหนได้ ภายใต้เงื่อนไขอะไร
Ablation
การทดลองถอดหรือเพิ่มทีละส่วนเพื่อดูว่าส่วนนั้นช่วยคะแนนจริงไหม
Pareto frontier
กลุ่ม entry ที่ไม่มีใครทั้งถูกกว่าและคะแนนสูงกว่า
Mock model
โมเดลปลอมที่ตอบตามสคริปต์ ใช้ทดสอบระบบโดยไม่เสียค่าโมเดล
